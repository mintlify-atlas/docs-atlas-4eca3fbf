## Overview

**Features** are the building blocks for usage-based billing and access control in Autumn. They represent measurable capabilities or resources that customers consume, such as:

- API calls
- Storage capacity
- Seats or users
- Credits or tokens
- Custom metered events

Features enable you to track usage, enforce limits, and bill customers based on their consumption.

## Feature Types

Autumn supports different feature types for various use cases:

### Metered Features

Metered features track continuous usage with automatic aggregation:

```json Example: API Call Feature
{
  "id": "api-calls",
  "name": "API Calls",
  "type": "metered",
  "config": {
    "filters": [
      {
        "property": "event_type",
        "operator": "equals",
        "value": ["api_call"]
      }
    ],
    "aggregate": {
      "type": "count",
      "property": null
    },
    "usage_type": "continuous"
  }
}
```

<Info>
Metered features automatically aggregate events from your application based on filter rules.
</Info>

### Credit System Features

Credit features act as a universal currency that can be spent across multiple metered features:

```json Example: Credit System
{
  "id": "credits",
  "name": "Credits",
  "type": "credit_system",
  "config": {
    "schema": [
      {
        "metered_feature_id": "api-calls",
        "credit_amount": 1
      },
      {
        "metered_feature_id": "storage-gb",
        "credit_amount": 100
      }
    ],
    "usage_type": "continuous"
  }
}
```

<Note>
Credit systems allow customers to allocate their balance flexibly across different resources.
</Note>

## Feature Configuration

All features share these core attributes:

<ParamField path="id" type="string" required>
  Unique identifier for the feature (e.g., `api-calls`, `storage`)
</ParamField>

<ParamField path="name" type="string">
  Human-readable name displayed to customers
</ParamField>

<ParamField path="type" type="string" required>
  Feature type: `metered` or `credit_system`
</ParamField>

<ParamField path="config" type="object" required>
  Configuration object specific to the feature type
</ParamField>

<ParamField path="display" type="object">
  Display settings for the feature
  
  <Expandable title="properties">
    <ParamField path="singular" type="string">
      Singular form (e.g., "API Call")
    </ParamField>
    <ParamField path="plural" type="string">
      Plural form (e.g., "API Calls")
    </ParamField>
  </Expandable>
</ParamField>

<ParamField path="event_names" type="array">
  Array of event names that trigger this feature's usage tracking
</ParamField>

## Metered Feature Configuration

Metered features use a configuration object with filters and aggregation:

### Filters

Filters determine which events count toward the feature:

<ParamField path="filters" type="array" required>
  Array of filter expressions
  
  <Expandable title="Filter Expression">
    <ParamField path="property" type="string">
      Event property to filter on
    </ParamField>
    <ParamField path="operator" type="string">
      Comparison operator: `equals`, `contains`, `greater_than`, etc.
    </ParamField>
    <ParamField path="value" type="array">
      Array of values to match against
    </ParamField>
  </Expandable>
</ParamField>

```json Example: Filter by Event Type
{
  "filters": [
    {
      "property": "event_type",
      "operator": "equals",
      "value": ["video_transcoded"]
    }
  ]
}
```

### Aggregation

Aggregation defines how events are counted:

<ParamField path="aggregate" type="object" required>
  Aggregation configuration
  
  <Expandable title="properties">
    <ParamField path="type" type="string">
      Aggregation type: `count`, `sum`, `max`, `unique`
    </ParamField>
    <ParamField path="property" type="string | null">
      Property to aggregate (null for count)
    </ParamField>
  </Expandable>
</ParamField>

```json Example: Sum Property Values
{
  "aggregate": {
    "type": "sum",
    "property": "duration_seconds"
  }
}
```

### Usage Type

<ParamField path="usage_type" type="string" required>
  How usage accumulates:
  - `continuous`: Usage accumulates over time (e.g., API calls)
  - `single`: One-time usage events (e.g., file uploads)
</ParamField>

## Credit System Configuration

Credit systems define conversion rates from credits to metered features:

<ParamField path="schema" type="array" required>
  Array of credit conversion rules
  
  <Expandable title="Credit Schema Item">
    <ParamField path="metered_feature_id" type="string">
      ID of the metered feature this credit can be spent on
    </ParamField>
    <ParamField path="credit_amount" type="number">
      How many credits are deducted per unit of the metered feature
    </ParamField>
  </Expandable>
</ParamField>

```json Example: Flexible Credit Schema
{
  "schema": [
    {
      "metered_feature_id": "api-calls",
      "credit_amount": 1
    },
    {
      "metered_feature_id": "storage-gb",
      "credit_amount": 100
    },
    {
      "metered_feature_id": "compute-hours",
      "credit_amount": 50
    }
  ]
}
```

<Note>
In this example, 1 API call costs 1 credit, 1 GB storage costs 100 credits, and 1 compute hour costs 50 credits.
</Note>

## Display Configuration

Customize how features appear to customers:

```json Example: Display Names
{
  "id": "api-calls",
  "name": "API Calls",
  "display": {
    "singular": "API Call",
    "plural": "API Calls"
  }
}
```

This enables proper pluralization in UI:
- "You have used 1 **API Call**"
- "You have used 100 **API Calls**"

## Event Tracking

Features automatically track usage when you send events via the [Track API](/api/track):

```typescript Example: Track API Call
await autumn.track({
  customer_id: "cus_123",
  event_name: "api_call",
  properties: {
    endpoint: "/users",
    method: "GET"
  }
});
```

The feature's filters determine whether this event increments usage.

### Event Names

Optionally specify which event names trigger the feature:

<ParamField path="event_names" type="array">
  Event names that contribute to this feature's usage
</ParamField>

```json Example: Multiple Event Names
{
  "id": "api-calls",
  "event_names": ["api_call", "api_request", "endpoint_hit"]
}
```

## Features and Entitlements

Features are connected to products through **entitlements**, which define:

- **Allowance**: Quota or limit (e.g., 10,000 API calls)
- **Interval**: Reset period (monthly, yearly, etc.)
- **Rollover**: Whether unused allowance carries over

See [Products and Plans](/concepts/products-and-plans) for details on entitlements.

```json Example: Feature → Entitlement → Product
{
  "feature": {
    "id": "api-calls",
    "type": "metered"
  },
  "entitlement": {
    "feature_id": "api-calls",
    "allowance": 10000,
    "interval": "month"
  },
  "product": {
    "id": "pro",
    "entitlements": ["ent_api_calls_10k"]
  }
}
```

## Environment Separation

Features are environment-specific:

<ParamField path="env" type="string" required>
  Environment identifier (`development`, `production`, etc.)
</ParamField>

<Warning>
Events sent to the `development` environment will only increment usage for development features.
</Warning>

## Archiving Features

Archive features instead of deleting them:

<ParamField path="archived" type="boolean" default="false">
  Whether the feature is archived
</ParamField>

Archived features:
- Stop accepting new usage events
- Preserve historical usage data
- Remain attached to existing entitlements

## Entity-Scoped Features

Features can be scoped to specific entities for granular tracking:

```typescript Example: Team-Scoped Storage
await autumn.track({
  customer_id: "cus_123",
  entity_id: "team_abc",
  event_name: "storage_used",
  properties: {
    bytes: 1073741824 // 1 GB
  }
});
```

See [Entities](/concepts/entities) for multi-tenant usage tracking.

## Common Patterns

### API Rate Limiting

```json
{
  "id": "api-calls",
  "name": "API Calls",
  "type": "metered",
  "config": {
    "filters": [
      {
        "property": "event_type",
        "operator": "equals",
        "value": ["api_call"]
      }
    ],
    "aggregate": {
      "type": "count",
      "property": null
    },
    "usage_type": "continuous"
  },
  "display": {
    "singular": "API Call",
    "plural": "API Calls"
  }
}
```

### Storage Tracking

```json
{
  "id": "storage-gb",
  "name": "Storage",
  "type": "metered",
  "config": {
    "filters": [
      {
        "property": "event_type",
        "operator": "equals",
        "value": ["storage_measurement"]
      }
    ],
    "aggregate": {
      "type": "max",
      "property": "gigabytes"
    },
    "usage_type": "continuous"
  }
}
```

<Note>
Using `max` aggregation ensures you track peak storage, not cumulative.
</Note>

```json
  "id": "credits",

        "metered_feature_id": "video-minutes",

    "usage_type": "continuous"
  }
}
```

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Can I change a feature's configuration after it's created?">
    Yes, but be cautious:
    - Changing filters affects which events count going forward
    - Historical usage data remains unchanged
    - Consider creating a new feature version for major changes
  </Accordion>

  <Accordion title="How do I track unique users instead of event count?">
    Use the `unique` aggregation type:
    ```json
    {
      "aggregate": {
        "type": "unique",
        "property": "user_id"
      }
    }
    ```
  </Accordion>

  <Accordion title="What's the difference between metered and credit_system features?">
    - **Metered features**: Track specific usage (API calls, storage, etc.)
    - **Credit features**: Universal currency that converts to metered features
    
    Use credits when you want customers to allocate a balance flexibly.
  </Accordion>

  <Accordion title="Can a single event increment multiple features?">
    Yes! An event can match filters for multiple features simultaneously:
    ```typescript
    await autumn.track({
      customer_id: "cus_123",
      event_name: "api_call",
      properties: {
        endpoint: "/premium/feature"
      }
    });
    ```
    This could increment both `api-calls` and `premium-api-calls` features.
  </Accordion>

  <Accordion title="How do I implement soft limits vs hard limits?">
    Features track usage, but enforcement is up to your application:
    
    **Soft limit** (warning):
    ```typescript
    const { allowed, usage } = await autumn.check({
      customer_id: "cus_123",
      feature_id: "api-calls"
    });
    
    if (usage > allowance * 0.9) {
      // Show warning at 90%
    }
    ```
    
    **Hard limit** (block):
    ```typescript
    if (!allowed) {
      throw new Error("Usage limit exceeded");
    }
    ```
  </Accordion>
</AccordionGroup>
